## 3. 計算ロジックの確認結果

### 3.1 譲渡益課税の根拠

実装は概ね正しい。

`simulation.ts` では、課税口座の取り崩し時に以下を計算している。

- 売却額
- 取得原価部分
- 実現譲渡益
- 売却時譲渡益税
- 源泉なし等の翌年扱い税額
- 普通口座オプションの申告対象損益
- 手取り額
- 理由
- 税務上の扱い

特定口座については、含み益比率を使って売却額のうち譲渡益部分を計算し、源泉ありの場合は 20.315% を売却時譲渡益税として控除している。

普通口座オプションについては、売却時に源泉徴収するのではなく、申告対象損益として翌年の所得税・住民税・国保等の計算に反映する扱いになっている。

また、普通口座オプションの「口座内積上げ利益」は、利益発生時に申告対象損益として記録し、同時に取得原価へ加算している。これにより、後で普通預金へ移動したときに同じ利益を二重課税しない設計になっている。

この方針は妥当。

### 3.2 注意点

譲渡益課税の根拠テーブルには、「課税なし」の普通口座移動も表示されている。

例:

- 普通口座利益移動
- 終了後戻し
- 不足補填売却だが、すでに申告対象化済みで実現譲渡益が0の移動

計算としては正しいが、「譲渡益課税の根拠」という見出しの中に「課税なし」が大量に並ぶと、ユーザーは「これは課税対象なのか、違うのか」を迷いやすい。

改善提案:

- 初期表示は「課税・申告に影響する行」だけに絞る。
  - `taxWithheld > 0`
  - `deferredTax > 0`
  - `declaredIncome > 0`
- `grossWithdrawal > 0` だが `realizedGain = 0` かつ `taxWithheld = 0` の行は、別の折りたたみ「課税されない資金移動」に分ける。
- 普通口座オプションの「利益発生」と「資金移動」を明確に分ける。
  - 利益発生: 申告対象損益
  - 資金移動: すでに課税対象化済みの原資移動

## 7. タイムパケットプランナーへの意見

ユーザーの感覚は正しい。

現在の実装は、基本情報の生年月日とシミュレーション開始年月から開始年齢を計算し、開始時点の年代以降の箱だけを表示している。

例:

- 開始時点が59歳の場合、50代以降だけを表示。
- 表示される箱は、やりたいことリスト、50代、60代、70代、80代。

この設計は、20代・30代のように人生イベントの時間軸が長い人には自然。

しかし、50代後半から60代以降の人にとっては、10年単位の箱が粗すぎる。

理由:

- 59歳の人にとって「50代」は実質的に今すぐの箱でしかない。
- 60代は10年が長すぎる。
- 退職後の体力・健康・家族状況・資産活用の判断は、10年単位より2年単位の方が現実に近い。
- 特に60歳から72歳を資産活用期間として見ているなら、その期間内を細かく切る方がアプリの目的に合う。

したがって、定年退職前後の世代では「年代バケット」ではなく「近い将来の実行時期バケット」に切り替える設計が望ましい。

## 8. タイムパケットの改善提案

### 8.1 推奨方針

タイムパケットは固定の年代箱ではなく、ユーザーの開始年齢に応じて箱を自動生成する。

基本方針:

- 若い人: 年代バケット
- 50代以降: 2年単位または健康寿命期バケット

### 8.2 表示モード

以下の2モードを用意する。

1. 年代モード
   - 20代、30代、40代、50代、60代、70代、80代
   - 主に20代から40代向け。

2. 退職後プランモード
   - すぐやる・準備中
   - 退職直後
   - 60〜61歳
   - 62〜63歳
   - 64〜65歳
   - 66〜67歳
   - 68〜69歳
   - 70〜72歳
   - 73歳以降
   - 保留

ユーザーが50歳以上、または資産活用集計期間が設定されている場合は、初期表示を「退職後プランモード」にする。

### 8.3 今回の自分用アプリに最も合う箱

現在の前提では、資産活用期間が60〜72歳なので、以下が自然。

- やりたいことリスト
- 今すぐ・準備中
- 60〜61歳
- 62〜63歳
- 64〜65歳
- 66〜67歳
- 68〜69歳
- 70〜72歳
- 73歳以降
- 保留・やらない

この形なら、退職後に先送りしすぎず、「健康なうちにやること」を2年単位で置ける。

### 8.4 「楽しみ支出へ変換」との連動

各箱には、変換時の初期実施年月を持たせる。

例:

- 60〜61歳の箱に入っている項目を「楽しみ支出へ」変換する場合:
  - 初期実施年月は本人が60歳になる月。
- 66〜67歳の箱:
  - 初期実施年月は本人が66歳になる月。
- 70〜72歳の箱:
  - 初期実施年月は本人が70歳になる月。
- 今すぐ・準備中:
  - 初期実施年月はシミュレーション開始年月。
- 保留:
  - 支出化ボタンは表示しない、または確認を挟む。

### 8.5 実装方針

現在の型は固定の `TimeBucketBucketId = "todo" | "20s" | ... | "80s"` になっている。

このままだと2年単位の箱を柔軟に追加しにくい。

推奨する型:

```ts
export type TimeBucketBucket = {
  id: string;
  label: string;
  kind: "todo" | "decade" | "ageRange" | "relative" | "later" | "hold";
  startAge?: number;
  endAge?: number;
  defaultYearMonthAge?: number;
};

export type TimeBucketItem = {
  id: string;
  title: string;
  bucketId: string;
  convertedSpecialExpenseId?: string;
  note?: string;
};
```

バケット定義は保存データに持たせてもよいが、まずはシナリオの基本情報から動的生成でよい。

### 8.6 既存データの移行

既存の `20s`、`30s`、`40s`、`50s`、`60s`、`70s`、`80s` はそのまま読み込めるようにする。

移行案:

- `todo` はそのまま。
- `50s` など既存の年代IDは、年代モードではそのまま表示。
- 退職後プランモードでは、既存の `60s` は `60〜61歳` などへ自動配置せず、最初は「60代から移行」などの箱にまとめてもよい。
- または、既存データが少ない前提なら、初回だけ手動で置き直す方が安全。

自分用アプリなら、無理な自動移行より、設計変更後に手で置き直す方が分かりやすい。

## 10. 結論

今回の実装は、計算ロジックと表示整理の方向性は正しい。

特に、譲渡益課税の根拠を内部計算明細から表示する実装は、品質確認に耐えられる形になっている。

一方で、タイムパケットの年代箱は、50代後半から60代のユーザーには粗すぎる。

このアプリの現在の目的が「60〜72歳の健康寿命期に、資産をどう使うかを見る」ことである以上、タイムパケットも10年単位ではなく、60〜72歳を2年単位で切る方が自然。

設計としては、年代モードを残しつつ、50歳以上では退職後プランモードを初期表示にするのが最もバランスが良い。
