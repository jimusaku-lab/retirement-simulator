# 入力導線・カード折りたたみ UX再設計

作成日: 2026-06-05

対象アプリ:

- 主対象: `apps/retirement-life-planner-public`
- 参照対象: `apps/retirement-life-planner`

## 1. 目的

一般向け版の現在の課題は、機能不足ではなく、入力画面と結果画面の情報量が多く、ユーザーが次に何をすべきか判断しにくい点にある。

この設計では、次の状態を目指す。

- ユーザーが最初に入力すべき項目を迷わない。
- 必須、推奨、詳細、専門補正の違いが画面上で分かる。
- 完了済みカードは要約だけ表示され、必要な時だけ展開できる。
- 入力後に、次に入力すべきカードへ自然に進める。
- 結果画面で気になった項目から、該当する入力カードや根拠カードへ戻れる。

## 2. 現状検証メモ

2026-06-05 に `http://127.0.0.1:5176/` の一般向け版を確認した。

主要入力タブの初期表示項目数は次の通り。

| 画面 | 表示状況 |
|---|---:|
| 基本情報 | 約42入力項目 |
| 初期資産 | 約62入力項目 |
| 生活費 | 約106入力項目 |
| 収入 | 約58入力項目 |
| 税・社会保険 | 詳細折りたたみはあるが、年度別根拠が大量に並ぶ |
| 結果 | 累計、税社保、NISA、月次表、年次表などが広く表示される |

良い点:

- 初回設定ウィザードは `家族 -> 資産 -> 収入 -> 支出 -> 前提 -> やりたいこと -> 結果` で自然な順序になっている。
- ダッシュボード先頭の「まず見る結論」は、最初に見るべき指標を出している。
- 税・社会保険タブでは、一部の専門入力と根拠表示が折りたたまれている。
- iDeCo一時金は「iDeCo受取方法」として表示され、単発入金より分かりやすくなっている。

主な問題:

- 通常入力画面では、標準入力と専門入力が同じ重さで並んでいる。
- 必須項目がカード単位で明示されず、どこまで入力すれば結果を見る価値があるか分かりにくい。
- カード入力後に、次に見るべきカードへ進む導線がない。
- 初回設定ウィザード完了後、通常入力画面のどこを補正すべきかがつながっていない。
- 結果画面で気になる数字から、原因となる入力項目へ戻る導線が弱い。

## 3. UX原則

### 3.1 1カード1判断

1つのカードは、ユーザーが1つの判断または入力単位を完了するための領域にする。

例:

- `現在資産` は標準入力。
- `取得原価と評価損益` は詳細入力。
- `一般口座オプション用の証拠金設定` は専門補正。

### 3.2 初期表示は標準入力だけ

初期表示で開くカードは、原則として次のいずれかに限定する。

- 未完了の必須カード
- ユーザーが直前にクリックした関連カード
- 結果に重大な注意が出ているカード

詳細入力、専門補正、原因調査用チャート、年度別根拠は閉じた状態を標準にする。

### 3.3 完了済みカードは要約化する

完了済みカードは全入力欄を見せず、折りたたみ時に次を表示する。

- 入力状態: `完了` / `未入力` / `要確認` / `詳細未設定`
- 主要値: 例 `現金・預金 800万円 / NISA 1,000万円 / iDeCo 500万円`
- 次アクション: 例 `取得原価を詳しく入れる`、`結果を見る`

### 3.4 自動ジャンプより「明示ボタン」を優先する

ユーザーが入力中に勝手にスクロールされると混乱する。

基本動作:

- 入力後に `次へ: 生活費を入力` のようなボタンを出す。
- そのボタンを押した時にだけ、次のカードを開いてスクロールする。
- 初回ウィザード内だけは、`次へ` で自動的に次ステップへ進む。

### 3.5 結果から入力へ戻れる

結果画面の注意カードには、対応する入力カードへのリンクを置く。

例:

- `税社保の注意年` -> 税・社会保険タブの該当年度根拠
- `90歳残高不足` -> 生活費、収入、資産活用期間、やりたいこと支出
- `iDeCo一時金の退職所得控除要確認` -> 収入タブのiDeCo一時金カード、税・社会保険タブの退職所得控除重複調整
- `取得原価未設定` -> 初期資産タブの取得原価カード

### 3.6 表示状態は4段階に分ける

画面上の情報は、常に全表示するか、完全に隠すかの二択にしない。ユーザーが今必要としている度合いに応じて、次の4段階で扱う。

| 表示状態 | 使う場面 | 画面上の扱い |
|---|---|---|
| 常時表示 | 現在の判断に必要な結論、次アクション、未完了の必須入力 | フル表示または先頭サマリー |
| 要約表示 | 入力済み、計算に使っていない、対象外、詳細未設定だが試算可能 | 1行から数行の状態表示だけ |
| 折りたたみ | 詳細入力、原因調査、専門補正、年度別根拠、コピー操作 | 閉じた `details` またはアコーディオン |
| 非表示 | 現在の前提では関係しない高度機能 | 通常は出さず、詳細モードや有効化時だけ出す |

重要なのは、`注意書きがあるからカードを全表示する` ではない。ユーザーが今そのカードを編集・判断する必要がない場合は、注意文ごとカードを要約表示または折りたたみにする。

### 3.7 「計算に使っていないカード」は要約表示にする

ある入力カードが存在していても、現在の設定では本計算に使われていない場合、そのカード全体を常時表示しない。

該当例:

- 年金受給プランナーを本計算へ反映している時の、外部公的年金イベント
- 初回サンプルで使っていない一般口座オプション用の詳細口座
- `試算のみ` の年金受給プランナー詳細
- 特定の収入・支出イベントが無効、対象外、または別カードに置き換えられている場合

表示方針:

- カード全体の入力欄は閉じる。
- 画面には短い状態行だけを出す。
- 状態行に `計算対象外`、`プランナー側を使用中`、`詳細を開く` を表示する。
- ユーザーがクリックした時だけ入力欄と説明文を展開する。

表示例:

```text
計算対象外: 本人の公的年金イベント
年金受給プランナーを本計算に反映中のため、このイベントは使っていません。
[詳細を開く] [プランナーを確認]
```

この場合、現在の長い注意文

```text
年金受給プランナーを反映中のため、この外部公的年金イベントは本計算では使っていません。年金額・受給開始年月は上のプランナー側を正として保存・計算します。
```

は、カードを開いた時だけ表示する。初期表示では短い状態行で十分とする。

### 3.8 注意文の表示ルール

注意文は、重要だから常時表示するのではなく、ユーザーの現在の判断に必要な時だけ常時表示する。

常時表示する注意:

- このままでは結果が大きく誤る可能性がある。
- 入力不足で計算が不安定または意味を持たない。
- 税区分や社会保険への反映を誤解すると判断を誤る。
- ユーザーが直前にクリックした数字の根拠である。

折りたたむ注意:

- 詳細な計算式の説明。
- すでに別カードへ置き換えられている入力の説明。
- 年度別、月別、口座別の内訳。
- コピー、同期、詳細補正など、通常入力では使わない操作説明。

注意文の長さ:

- 常時表示は原則2行以内。
- 長い説明は `詳しい理由を見る` の中に置く。
- 同じ意味の注意を複数カードで繰り返さない。

### 3.9 いつでも表示すべきもの

ユーザーに常時見せるべきものは、すべての入力欄ではなく、現在の判断に必要な状態である。

常時表示する:

- 画面名と現在のシナリオ名
- 入力状況サマリー
- 次に入力・確認すべき項目
- 結果を見る上で不足している必須入力
- 現在のカードの要約
- ダッシュボードの結論と次アクション

常時フル表示しない:

- 完了済みカードの全入力欄
- 計算に使っていないイベントカード
- 詳細な制度説明
- 年次・月次の全明細
- 他シナリオ反映などの管理操作

### 3.10 入力後は次カードを視覚的に促す

ユーザーが1つのカードを入力したら、次に必要なカードが分かるようにする。単に上部サマリーへ文字で出すだけでは弱いため、カード自体にも視覚的な促しを入れる。

基本動作:

1. 現在カードの必須項目が満たされる。
2. 現在カードを `完了` または `確認推奨` に更新する。
3. 次に必要なカードを `next_required` とする。
4. 次カードの枠色、ラベル、ボタンで促す。
5. 画面移動は勝手に行わず、`次へ` ボタンを押した時に展開・スクロールする。

同じ画面内に次カードが見えている場合:

- 次カードの枠を強調する。
- カード上部に `次に入力` ラベルを出す。
- 折りたたみカードなら、要約行を強調する。

次カードが別タブまたは画面外にある場合:

- 入力状況サマリーに `次に入力: 生活費` を表示する。
- 現在カード末尾に `次へ: 生活費を入力` ボタンを出す。
- 対象サブタブにも小さな `次` バッジを出す。
- ボタン押下後に対象カードを開き、スクロールし、数秒だけ強調状態にする。

### 3.11 枠色とラベルのルール

カードの色は装飾ではなく状態表示として使う。色だけに頼らず、必ずラベルも併記する。

| 状態 | 枠色の考え方 | ラベル |
|---|---|---|
| 現在編集中 | 青系 | `編集中` |
| 次に入力 | アンバー系 | `次に入力` |
| 不足あり | 赤系 | `不足あり` |
| 確認推奨 | アンバー系の薄い表示 | `確認推奨` |
| 完了 | 緑系の控えめ表示 | `完了` |
| 計算対象外 | グレー系 | `計算対象外` |
| 結果から遷移 | 青系の強調 | `確認中` |

使い分け:

- `次に入力` は、ユーザーの次行動を促す最重要の視線誘導に使う。
- `不足あり` は、結果の信頼性に影響する必須不足だけに使う。
- `確認推奨` は、入力しなくても試算できるが精度や判断に効く項目に使う。
- `完了` は強く主張させない。完了カードが目立ちすぎると、次に必要なカードが埋もれる。
- `計算対象外` は、カードを小さく見せる。これにより、ユーザーに「ここを全部見なくてよい」と伝える。

アクセシビリティ:

- 色だけで意味を伝えない。
- ラベル、要約文、ボタン文言で同じ意味を伝える。
- 枠色の強調は、入力後数秒で落ち着いた表示へ戻してよい。

### 3.12 入力フロー例

通常入力での理想的な流れ:

1. `家族・期間` が未完了なら、そのカードを開き、枠に `不足あり` を出す。
2. ユーザーが生年月日、開始年月、終了年齢を入力する。
3. `家族・期間` は要約表示に変わる。
4. `現在資産` カードの枠がアンバー系になり、`次に入力` ラベルが出る。
5. 現在カード末尾に `次へ: 現在資産を入力` を出す。
6. 押すと `現在資産` が開き、画面がスクロールする。
7. 資産入力後は `生活費` が `次に入力` になる。

この流れにより、ユーザーに「全部のカードを順番に読ませる」のではなく、「次に必要なカードだけを追わせる」体験にする。

### 3.13 初期表示で全カード全展開しない

現在の画面のように、PC画面を覆うほど複数カードを全体表示する状態は、一般向け版の標準表示としては不可とする。

初期表示の上限:

- 各入力タブで、フル表示するカードは原則1カード。
- 例外的に、入力状況サマリー + 次に入力すべきカードの2つまでは許容する。
- それ以外のカードは、要約表示または折りたたみ表示にする。
- 詳細、専門補正、原因調査、コピー操作、年度別根拠は初期状態で必ず閉じる。

カード一覧の見せ方:

- すべてのカード見出しは見えてよい。
- ただし、入力欄や長い説明文は常時表示しない。
- 見出し、状態ラベル、主要値、`開く` ボタンだけを見せる。
- ユーザーがカードをクリックした時に、そのカードの入力欄と説明を展開する。

繰り返しカードの扱い:

- 収入イベント、特別支出、世帯メンバー、退職所得履歴など、複数件並ぶカードは全件を初期展開しない。
- 初期表示では各イベントを1行要約にする。
- 編集中の1件、未入力がある1件、結果から指定された1件だけを展開する。

この方針により、画面上でユーザーが「全部を読まなければならない」と感じる状態を避ける。

### 3.14 入力状況サマリーは常時アクセスできる

入力状況サマリーは、ユーザーが偶然 `結果` や特定タブを押した時だけ見つけるものにしない。

表示ルール:

- `安全性シミュレーション` の全サブタブ上部に表示する。
- `ダッシュボード` と `結果` には、入力状況サマリーの簡易版を表示する。
- 必須入力が未完了、または確認推奨が残っている場合は、ヘッダー付近に `入力ガイド` または `次に確認` の導線を出す。
- `入力ガイド` を押すと、入力状況サマリーへスクロールする。
- 初回設定ウィザード完了後は、ダッシュボードに `次に確認するとよい項目` を1つだけ表示する。

サマリーは「入力画面にある便利機能」ではなく、「アプリ全体の案内役」として扱う。

### 3.15 進捗カウントは意味を明示する

`6/6 完了` のような表示だけでは、初回ユーザーには意味が分からない。必ず分母と対象を説明する。

表示例:

```text
必須入力
6項目中6項目完了
```

または、すべて完了している場合:

```text
必須入力は完了
6項目すべて入力済み
```

補足導線:

- `内訳を見る` を置く。
- 内訳には、家族・期間、現在資産、毎月の生活費、公的年金、税金・社会保険の計算方法など、対象カード名を表示する。
- `必須入力` と `確認推奨` を混ぜない。

注意:

- 必須が完了しているのに、確認推奨項目を `次に入力` とだけ表示すると、必須不足のように誤解される。
- 必須完了後の推奨項目は、`次に確認するとよい` または `おすすめ確認` と表示する。

表示例:

```text
必須入力は完了
6項目すべて入力済み

次に確認するとよい
iDeCo受取
iDeCo残高600万円の受取方法が未確認です
```

### 3.16 次カードはカード全体をクリック可能にする

入力状況サマリーの `次に入力` または `次に確認するとよい` 枠は、単なる表示ではなく、カード全体をクリックできるナビゲーションにする。

動作:

1. ユーザーが `次に確認するとよい: iDeCo受取` の枠をクリックする。
2. アプリは `安全性シミュレーション -> 収入` タブへ切り替える。
3. `iDeCo受取` カードを展開する。
4. `iDeCo受取方法` など、最初に必要な入力欄へスクロールする。
5. 可能ならその入力欄へフォーカスする。
6. 対象カードに `ここを入力` または `確認推奨` ラベルを数秒間強調表示する。

ボタン文言:

- 必須未完了の場合: `ここを入力する`
- 推奨確認の場合: `ここを確認する`
- iDeCoの場合: `iDeCo受取を入力する`

### 3.17 タブの `次` マークは説明と移動を兼ねる

タブに小さく `次` と出すだけでは意味が弱い。初回ユーザーが見ても分かるように、タブバッジは次の動作を持たせる。

表示:

- `収入` タブに `次` バッジを出す。
- 可能なら `次: iDeCo` の短いツールチップを出す。
- モバイルでは `収入` の横に小さく `次` を出す。

動作:

- `収入` タブを押すと、通常の収入タブ先頭ではなく、次対象の `iDeCo受取` カードへスクロールする。
- ただし、ユーザーが明示的に別カードを開いている場合は、その操作を尊重する。

### 3.18 入力導線の状態名

サマリーとカードで使う文言は、ユーザーの心理負担を下げるために区別する。

| 状態 | 使う文言 | 意味 |
|---|---|---|
| 必須未入力 | `次に入力` | 結果を見る前に入れるべき |
| 必須完了 + 推奨あり | `次に確認するとよい` | 試算は可能だが精度や判断に効く |
| 専門項目 | `必要なら確認` | 通常ユーザーは飛ばしてよい |
| 対象外 | `計算対象外` | 今は見なくてよい |

今回の例では、必須入力が `6項目中6項目完了` しているため、iDeCo受取は `次に入力` ではなく、`次に確認するとよい` と表現する方が自然である。

## 4. 入力カード状態モデル

各入力カードに、少なくとも次の状態を持たせる。

```ts
type InputCardPriority = "required" | "recommended" | "detail" | "expert";

type InputCardVisibility =
  | "always"
  | "summary"
  | "collapsed"
  | "hidden";

type InputCardHighlight =
  | "none"
  | "current"
  | "next_required"
  | "review"
  | "blocked"
  | "targeted";

type InputCardStatus =
  | "not_started"
  | "incomplete"
  | "complete"
  | "review_recommended"
  | "not_applicable"
  | "inactive";

type InputCardDefinition = {
  id: string;
  title: string;
  priority: InputCardPriority;
  status: InputCardStatus;
  visibility: InputCardVisibility;
  highlight: InputCardHighlight;
  summary: string;
  missingItems: string[];
  nextCardId?: string;
  defaultExpandedReason?: "first_missing" | "user_target" | "result_warning";
};
```

この定義は、最初はUI内の派生データでよい。計算ロジックや保存データへ無理に組み込まない。

`status` と `visibility` は別の概念として扱う。

- `status`: 入力や確認の状態。
- `visibility`: 画面上でどれだけ見せるか。

例:

- 入力済みの生活費カード: `status = complete`, `visibility = summary`
- 未入力の生活費カード: `status = incomplete`, `visibility = always`
- 年金プランナー反映中の外部公的年金イベント: `status = inactive`, `visibility = summary`
- 一般口座オプション未利用時の詳細カード: `status = not_applicable`, `visibility = hidden`

`highlight` は、ユーザーの視線誘導のために使う。

- `current`: いま編集中のカード。
- `next_required`: 次に入力すべきカード。
- `review`: 入力済みだが確認推奨のカード。
- `blocked`: 結果を見る前に不足があるカード。
- `targeted`: 結果やサマリーから遷移してきたカード。

## 5. 必須入力判定

初期導入では、次を必須判定の対象にする。

| 分類 | 必須項目 | 条件 |
|---|---|---|
| 家族・期間 | 本人年齢または生年月日、開始年月、終了年齢または終了年月 | 常に必須 |
| 目標 | 残高確認年齢、目標残高 | 常に推奨。未入力でも試算可 |
| 資産 | 現金・預金、NISA、iDeCo、課税口座、負債 | 金額0でも入力済み扱い可 |
| 生活費 | 毎月生活費 | 常に必須 |
| 収入 | 年金見込み額、受給開始年齢 | 常に必須 |
| iDeCo | 受取方法 | iDeCo残高がある場合は確認推奨 |
| iDeCo一時金 | 受取年月、一時金受取額、加入年数、退職所得の申告 | iDeCo一時金を選んだ場合は必須 |
| 税社保 | 自動計算 / 自動計算 + 補正 / 手入力 | 常に必須 |
| 特別支出 | 金額と年月 | 登録済み支出がある場合だけ必須 |

未入力でも計算できる項目は、`警告` ではなく `詳細未設定` または `確認推奨` とする。

## 6. 推奨カード順

通常入力画面の体験は、次の順序に寄せる。

1. 入力状況サマリー
2. 家族・期間
3. 現在資産
4. 生活費
5. 年金・給与・iDeCo・退職金
6. 税金・社会保険の計算方法
7. 特別支出・やりたいこと
8. 結果を見る

現在のタブ分割を一度に大きく変えなくてもよい。初期導入では、`安全性シミュレーション` 内のサブタブ上部に入力状況サマリーを置き、各サブタブ内カードを上記の考え方で折りたたむ。

### 7.5 収入

初期表示で開く:

条件付きで開く:

折りたたみ:

- `年金受給プランナー`
- `退職後の給与・パート`
- `その他収入イベント`

公的年金の表示ルール:

- 年金受給プランナーを `反映する` にしている場合、本人・配偶者の外部公的年金イベントは計算に使われない。
- この状態では、外部公的年金イベントのカード全体を表示しない。
- 代わりに、`計算対象外: 年金受給プランナー側を使用中` という要約行だけを表示する。
- 入力欄と長い説明文は、ユーザーが `詳細を開く` を押した時だけ表示する。
- `プランナーを確認` ボタンで年金受給プランナーカードへ移動できるようにする。

表示例:

```text
計算対象外: 本人の公的年金イベント
年金受給プランナーを反映中のため、年金額と受給開始年月はプランナー側を使っています。
[詳細を開く] [プランナーを確認]
```

この要約行は、ユーザーに「このカードを全部見なくてよい」と伝えるためのもの。カードを覆うような長い注意文を初期表示しない。

年金受給プランナーの表示ルール:

- プランナーを本計算に反映している場合は、標準カードとして要約を表示する。
- プランナーが `試算のみ` の場合は、詳細扱いにし、必要時だけ開く。

- 収入イベントは全件を初期展開しない。

iDeCo受取カードでは、次の説明を必ず出す。

- 年金受取は公的年金等の雑所得として扱う。
- 一時金は退職所得として扱う。

## 8. カード展開ルール

優先順位:

1. URLまたは画面遷移で指定されたカードを開く。
2. 結果画面からのリンクで指定されたカードを開く。
3. 未完了の必須カードのうち、順序が最も早いカードを開く。
4. 重要な確認推奨カードを1つだけ開く。
5. すべて完了していれば、最後にユーザーが開いたカードを維持する。
6. それもなければ、各タブの先頭標準カードだけ開く。

自動で複数カードを展開しない。

カード強調ルール:

1. 結果やサマリーから移動したカードは `targeted` として強調する。
2. 未入力の必須カードのうち最初の1つは `next_required` として強調する。
3. 現在ユーザーが編集しているカードは `current` として強調する。
4. `blocked` は、結果を見る上で必須不足があるカードだけに使う。
5. `review` は、iDeCo一時金の加入期間、取得原価、税社保補正など、確認すれば精度が上がる項目に使う。

同時に強調するカードは最大2つまでにする。

- `current` と `next_required`
- `targeted` と `review`

多数のカードを色付きにすると、ユーザーは何を見ればよいか分からなくなる。

## 9. 導入工程

### Phase 15-A: カード状態と入力状況サマリー

目的: 画面構造を大きく壊さず、次に何をすべきかを表示する。

作業:

- 入力カード定義を作る。
- 必須、推奨、詳細、専門補正を判定する。
- `安全性シミュレーション` の上部に入力状況サマリーを追加する。
- `次の未入力へ` ボタンで対象タブ・カードへ移動する。

完了条件:

- 未入力または確認推奨のカードが分かる。
- 主要入力が不足している場合、結果を見る前に警告できる。

### Phase 15-B: 入力カードの折りたたみ

目的: 入力タブの情報密度を下げる。

作業:

- 基本情報、初期資産、生活費、収入、税・社会保険のカードを標準/詳細/専門に分ける。
- 完了済みカードは要約表示にする。
- 詳細カードは初期状態で閉じる。
- iDeCo、退職所得、税社保など条件付き重要カードは必要時だけ開く。

完了条件:

- 初期資産、生活費、収入で、初期表示の入力欄数が大幅に減る。
- ユーザーが詳細を見たい時は明示的に開ける。

### Phase 15-C: 結果・ダッシュボードの原因調査導線

目的: 結果から該当入力・根拠へ戻れるようにする。

作業:

- ダッシュボードに `次に確認すること` を追加する。
- 結果画面の主要注意から該当タブ・カードへ移動するリンクを追加する。
- 原因調査用チャートと大きな表を折りたたむ。

完了条件:

- ユーザーが「なぜこの数字か」を見たい時に、該当箇所へ移動できる。
- 結果画面の初期表示が結論中心になる。

### Phase 15-D: QAと表示検証

目的: 折りたたみで入力欄が隠れすぎていないか、逆に見えすぎていないかを確認する。

確認項目:

- PC幅とスマートフォン幅で横スクロールが出ない。
- 初回設定を使わず通常入力から始めても、次に何を入れるか分かる。
- 初回設定後、詳細入力の案内が分かる。
- iDeCo一時金、退職所得、税社保注意年から該当根拠へ移動できる。
- `npm --prefix apps/retirement-life-planner-public run test -- src/lib/simulation.test.ts` が成功する。
- `npm --prefix apps/retirement-life-planner-public run build` が成功する。

## 10. 非対象

- iDeCo退職所得控除の制度ロジック変更
