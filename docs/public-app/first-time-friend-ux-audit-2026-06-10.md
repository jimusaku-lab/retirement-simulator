# 初めて触る友人向け UX監査（2026-06-10）

## 目的

友人に一般向け版を試してもらう前提で、初めて触るユーザーが迷わず入力できるかを確認した。

対象:

- 主対象: `apps/retirement-life-planner-public`
- 確認URL: `http://localhost:5176/`
- 参照コード:
  - `apps/retirement-life-planner-public/src/App.tsx`
  - `apps/retirement-life-planner-public/src/components/OnboardingWizard.tsx`
  - `apps/retirement-life-planner-public/src/components/TimeBucketPlanner.tsx`
  - `apps/retirement-life-planner-public/src/data/sampleData.ts`

## 総評

初回設定ウィザード、入力ガイド、カード折りたたみ、資産活用から特別支出への変換など、主要な仕組みは入っている。

ただし、初めて触るユーザー視点ではまだ不十分。特に問題なのは、ユーザーが入力していないサンプル由来の値が残ること、生活費の「その他」が大きくなりやすいこと、資産活用と特別支出の理想的な入力順が画面上で明確でないこと。

友人テスト前に優先して直すべき。

## 現在確認できた状態

### 初回起動

初回起動では、最初に「データの扱い」確認モーダルが出る。その後、初回設定ウィザードが出る。

良い点:

- 端末内保存・共有されないことを最初に説明している。
- 初回設定ウィザードは `家族 -> 資産 -> 収入 -> 支出 -> 前提 -> やりたいこと -> 結果` の順で自然。
- ウィザードを閉じた後も、画面左下に `初回設定` ボタンが出る。

問題:

- 初回設定ボタンは画面左下の小ボタンで、メイン導線としては見つけにくい。
- 初回ウィザードの背後に既存サンプルのダッシュボードや入力ガイドが存在しており、初回ユーザーには「これは自分の入力結果なのか、サンプルなのか」が分かりにくい。
- 初回設定の結果がかなり厳しめで、資産寿命が75歳台、90歳残高が大きくマイナスになる。友人テストの第一印象としてはネガティブになりやすい。

## 個別論点

### 1. 初期資産の「毎月の追加投資」

重要な問題あり。

一般向け版の初期サンプルには `NISA積立` として毎月5万円の追加投資が入っている。

```ts
assetContributionEvents: [
  {
    name: "NISA積立",
    monthlyAmount: 50_000,
    ...
  }
]
```

さらに、初回設定ウィザードを保存しても `assetContributionEvents` は初期化されていない。そのため、ユーザーがウィザードで追加投資を入力していなくても、サンプル由来の毎月5万円積立が残る可能性がある。

これは友人テスト前に直すべき。

ユーザー視点の問題:

- 「毎月の追加投資」が初期資産入力の下の方にあり、存在に気づきにくい。
- 自分で入力していない積立が計算に入ると、資産寿命やNISA未実行額の理由が分からない。
- 「追加投資」は現在資産ではなく、将来の積立予定だが、初期資産タブの下にあるため意味を誤解しやすい。

設計方針:

- 初回設定保存時は、サンプル由来の `assetContributionEvents` をクリアする。
- ウィザードに `毎月の追加投資を入れるか` を明示的に追加するか、初期値は0にする。
- 初期資産タブでは「毎月の追加投資」ではなく、`将来の積立予定` または `毎月の積立・追加投資予定` と表示する。
- 説明は「現在資産ではなく、開始月以降に毎月投資する予定額です。生活費や税社保を払った後の資金から実行されます」とする。
- 追加投資が0でない場合、入力状況サマリーで `追加投資予定あり` と明示する。

優先度: P0

### 2. 生活費の「その他」集中

現行ウィザードは、毎月の生活費合計から住宅費と医療・介護費を差し引き、残りを `その他` に入れる。

```ts
other = total - housing - healthMedical
```

したがって、現在コード上は「住宅費までその他に重複して入る」設計ではない。

ただし、ユーザー体験としては問題が残る。

問題:

- 初回ウィザードでざっくり入れた生活費は、食費・日用品・通信費・光熱費などに分かれず、ほぼ `その他` に集まる。
- 生活費タブには説明文があるが、入力状況サマリーでは `生活費 完了` になってしまう。
- 「その他に大きく入っているので、あとで費目別に分けると精度が上がる」という促しが弱い。

設計方針:

- `その他` が生活費全体の50%以上なら、入力状況サマリーで `確認推奨: 生活費の内訳` を出す。
- 生活費タブ先頭に `未分類生活費` カードを出す。
- `その他` の名称を、初回ウィザード由来の場合だけ `その他（未分類）` と表示する。
- 食費・日用品・通信費・光熱費へ分けるクイック分解ボタンを用意する。
- ユーザーが「ざっくりで進む」を選べるようにし、必須扱いにはしない。

優先度: P0

### 3. 年齢別生活費変更・世帯構成変更の説明不足

現行ウィザードには `年齢別生活費変更` があり、標準では `70歳以降少し下げ、75歳以降医療費を増やす` が選ばれている。

生活費タブにも `年齢別の生活費変更` の折りたたみがある。

基本情報には、同居状態変更・税扶養・国保変更の入力欄がある。

問題:

- これらが「将来シミュレーションで重要な変化点」だと初回ユーザーに伝わりにくい。
- 生活費タブ側では、同居状態変更が登録されている場合だけ表が出る。未登録時に「将来、子どもの独立・別居・介護施設・配偶者の状況変化があればここを考える」という促しが弱い。
- ユーザーは、毎月生活費を一つ入れたらそれで完了と思いやすい。

設計方針:

- 生活費タブに `将来の生活費変化チェック` を追加する。
- 表示項目は以下。
  - 70歳以降の生活費低下
  - 75歳以降の医療・介護費増
  - 子どもの独立・別居
  - 住宅ローン終了・家賃変化
  - 車の所有終了・買替
  - 配偶者の就労終了・介護
- `該当なし` と `後で設定` を選べるようにする。
- 該当ありなら該当カードへ誘導する。

優先度: P1

### 4. 収入イベント入力の初期導線

現行ウィザードは、年金、給与・パート、iDeCo、退職金を同じ収入ステップに置いている。

良い点:

- 給与・パート等（月額）の入力欄は存在する。
- ウィザードで給与額を入れると給与イベントが作成される。

問題:

- アプリの出自が退職後想定のため、通常入力では年金・iDeCoの確認が前面に出やすい。
- まだ退職していない一般ユーザーにとっては、最初に給与・賞与・退職予定日を入れる流れの方が自然。
- 入力状況サマリーでは、公的年金が必須、iDeCoが推奨として出るが、給与がない人・ある人の分岐が弱い。

設計方針:

- 初回ウィザード冒頭に `現在の状態` を追加する。
  - 退職前
  - 退職済み
  - 退職後も働く
  - 年金生活中
- `退職前` の場合は、収入ステップの主導線を `給与・賞与 -> 退職予定 -> 退職金 -> 年金見込み -> iDeCo` にする。
- `退職済み` の場合は、`年金 -> iDeCo -> その他収入` を主導線にする。
- 入力状況サマリーも persona に応じて必須・推奨を変える。

優先度: P1

### 5. 税・社会保険タブの情報量

現行の税・社会保険タブは、上部要約と詳細折りたたみがあり、以前より改善されている。

良い点:

- 詳細根拠、後期高齢者医療、所得水準別テーブルは折りたたみになっている。
- 退職所得控除の重複調整は `確認済み` ボタンがある。
- 年度ベースと支払年の違いを説明している。

問題:

- `申告不要・申告確認の判定` は、同じ文言が年度別・メンバー別に縦に並びやすい。
- ほとんど変化がない年度まで表示されるため、確認すべき青・黄の行が埋もれる。
- 友人テストでは、税タブを開いた瞬間に「専門的で難しい」と感じる可能性がある。

設計方針:

- 初期表示は `変化点だけ` にする。
- 通常行は、同じ判定が連続する年度をまとめる。
  - 例: `2033〜2042年: 申告不要制度の可能性`
- `年金以外20万円超`、`税額発生`、`住民税申告注意` などの変化年だけカード表示する。
- 全年度表は `全年度の判定表を開く` の中へ入れる。

優先度: P1

### 6. 特別支出と資産活用ビューの接続

現行の資産活用ビューには、タイムバケットでやりたいことを追加し、`支出へ` から特別支出へ変換する機能が入っている。

確認できた機能:

- タイムバケットにやりたいことを追加できる。
- `支出へ` から、年月・金額・カテゴリ・計算方式を入れて特別支出化できる。
- 特別支出側では、タイムバケット由来の項目に `タイムバケット由来` ラベルが出る。
- 特別支出側から `タイムバケットへ` 戻るボタンもある。

問題:

- 安全性シミュレーションの `特別支出` タブを先に見ると、いきなり支出入力フォームに見える。
- このアプリの中心思想である「やりたいことを整理し、実行するものだけ支出化する」流れが、特別支出タブの先頭で十分に示されていない。
- 特別支出が空、または楽しみカテゴリがない場合、資産活用ビューへ誘導するべき。

設計方針:

- 特別支出タブの先頭に `やりたいことから作る` カードを置く。
- 文言は、通常説明ではなく行動導線にする。
  - `旅行・趣味・家族イベントなどは、資産活用のタイムバケットで整理してから、計算に入れるものだけ特別支出に変換できます。`
  - ボタン: `資産活用でやりたいことを整理`
- 特別支出が0件、または楽しみカテゴリ0件なら、このカードを強調表示する。
- 既に特別支出がある場合は、タイムバケット由来か手入力かを一覧で区別する。

優先度: P0

### 7. 初回設定メニューの発見性

現行では、初回設定は初回自動表示され、閉じた後は画面左下の固定ボタンから再表示できる。

問題:

- 左下固定ボタンは見つけにくい。
- ヘッダーの主要操作に `初回設定` がない。
- ユーザーが「ウィザードをどこから開くか分からない」と感じやすい。

設計方針:

- ヘッダーまたは入力ガイド内に `初回設定をやり直す` を常設する。
- 左下ボタンは補助導線として残してよいが、主導線にはしない。
- `データ` タブにも `初回設定をやり直す` を置く。

優先度: P1

### 8. 初期サンプル値が厳しすぎる

確認した初回ウィザードの標準値では、結果が以下のように出た。

- 資産寿命: 75歳9か月
- 90歳時点残高: -3,066万円
- 平均月次取り崩し: 20万円

ダッシュボード上のサンプルでも、資産寿命は73歳11か月、90歳残高は大きくマイナス。

問題:

- 初めて触る人が「このアプリは怖い数字を出すもの」と感じやすい。
- 入力練習用の標準ケースとしては、最初から破綻寄りすぎる。
- 友人テストでは、UX評価の前に不安や反発が出る可能性がある。

設計方針:

- 初期サンプルは `まず成立する標準ケース` にする。
- 90歳時点で目標残高を少し上回る程度にする。
- 厳しめケースは別シナリオ `厳しめケース` として用意する。
- ダッシュボードには `これは入力練習用の匿名サンプルです` を明示する。
- 初回設定結果も、標準値のままなら大きく破綻しないようにする。

優先度: P0

## 改善優先順位

### P0: 友人テスト前に必須

1. 初回設定保存時に、サンプル由来の毎月追加投資を残さない。
2. 「毎月の追加投資」を `将来の積立予定` として説明し、現在資産とは別物だと明示する。
3. 生活費の `その他` が大きい場合、`未分類生活費` として確認推奨にする。
4. 特別支出タブから資産活用・タイムバケットへ誘導する。
5. 初期サンプル値を、最初から大幅ショートしない入力練習用ケースへ調整する。

### P1: 友人テストの質を上げる

1. 退職前・退職済みなどのユーザー状態に応じて、収入入力の順序と必須項目を変える。
2. 年齢別生活費変更・世帯構成変更を `将来の変化チェック` として促す。
3. 税・社会保険の申告確認表を、変化点だけ初期表示にする。
4. 初回設定をヘッダーまたは入力ガイドから再開できるようにする。
5. 入力ガイドの文言を自然にする。

### P2: さらに磨く

1. 生活費のクイック分解テンプレートを複数用意する。
2. 初回ウィザード結果から、弱い原因へ直接ジャンプする。
3. サンプルシナリオに `標準`、`安全寄り`、`厳しめ` の説明を付ける。
4. モバイルで入力ガイドを下部固定の小さな導線にする。

## 友人テストで確認する質問

- 初回設定がどこから始まるか迷わなかったか。
- 自分が入力していない値が計算に入っていると感じた箇所はあったか。
- `毎月の追加投資` が何を意味するか分かったか。
- 生活費の `その他` を細かく分けた方がよいと分かったか。
- 退職前の場合、給与・退職金・年金・iDeCoの入力順は自然だったか。
- 特別支出は、直接入力するより先に、やりたいこと整理から入る意味が分かったか。
- 税・社会保険タブで、確認すべき年と無視してよい詳細の区別ができたか。
- 初回設定をもう一度開く場所が分かったか。
