# 確認推奨カードの確認済み設計

作成日: 2026-06-08

## 1. 背景

入力状況サマリーで `確認推奨` と表示されるカードは、入力不足とは別の意味を持つ。

例として、`退職所得控除の重複調整` は、過去退職金とiDeCo一時金の重複調整が発生している場合に表示される。これは計算上の注意対象であり、入力欄を埋め直しても、重複調整そのものが存在する限り `確認推奨` のまま残る。

現状は、ユーザーが該当カードを開いて内容を確認しても、その事実を保存する仕組みがない。そのため、ユーザーから見ると「何をすれば黄色が消えるのか」が分からない。

## 2. 現状の問題

現状の判定:

- `review_recommended` は、データ状態から毎回自動判定される。
- `退職所得控除の重複調整` は、重複調整対象が1件以上あると `review_recommended` になる。
- カードを開いた、詳細を読んだ、入力を修正した、ダッシュボードへ戻った、という操作では状態が変わらない。
- `確認済み` を保存するユーザー操作・状態がない。

ユーザー視点の問題:

- 黄色が「未入力」なのか「注意点あり」なのか分かりにくい。
- 既に確認した後も黄色が残るため、作業が終わった感覚にならない。
- ダッシュボードへ戻っても同じ警告が残り、入力が未完了のように見える。
- 専門補正カードは、入力完了ではなく確認完了を扱うべきなのに、その状態がない。

## 3. 設計方針

`確認推奨` と `確認済み` を明確に分ける。

| 状態 | 意味 | 表示 |
|---|---|---|
| 未入力 | 必須項目が足りない | 赤系、入力を促す |
| 確認推奨 | 計算上の注意点があり、まだユーザーが確認済みにしていない | 黄系、確認を促す |
| 確認済み | 注意点は残っているが、ユーザーが内容を確認した | 緑または中立色、完了扱い |
| 対象外 | 注意点がない | 非表示または要約 |

重要:

- `確認済み` は、注意点が消えたという意味ではない。
- `確認済み` は、ユーザーがその注意点を見て受け入れた、または後で専門家へ確認する前提で作業を進めることを意味する。
- 入力内容が変わり、確認した根拠が変わった場合は、再び `確認推奨` に戻す。

## 4. 対象カード

初期対象:

- `退職所得控除の重複調整`
- `iDeCo一時金` の加入開始日/終了日が任意だが未入力の場合
- `NISA・iDeCo・特定口座などの評価額と評価損益` の取得原価確認

将来対象:

- 税・社会保険の専門補正
- 一般口座サブ口座の詳細管理
- 結果画面から戻る原因調査カード

## 5. UI仕様

### 5.1 入力状況サマリー

確認推奨カードには、次の表示を出す。

未確認時:

```text
確認推奨
退職所得控除の重複調整
重複調整 1件を確認
[確認する]
```

確認済み時:

```text
確認済み
退職所得控除の重複調整
重複調整 1件を確認済み
[再確認する]
```

確認済みカードは、黄色の次対象から外す。詳細一覧には `確認済み` として残してよい。

### 5.2 対象カード内

カードを開いただけでは確認済みにしない。

カード内に明示ボタンを置く。

```text
[この内容を確認済みにする]
```

ボタン付近には短い説明を置く。

```text
内容を確認済みにすると、入力状況サマリーでは未確認扱いから外れます。金額や日付を変更すると再確認が必要になります。
```

### 5.3 確認済みの解除

確認済み後も、ユーザーが再確認できるようにする。

- `再確認する` で対象カードへ移動する。
- 必要なら `確認済みを解除` を置く。
- ただし通常操作では、入力値の変更により自動で未確認へ戻る設計を優先する。

## 6. データ設計

シナリオ単位で確認済み状態を保存する。

追加案:

```ts
type ReviewAcknowledgement = {
  cardId: InputCardId;
  fingerprint: string;
  acknowledgedAt: string;
};

type ScenarioData = {
  reviewAcknowledgements?: ReviewAcknowledgement[];
};
```

`fingerprint` は、確認対象の根拠データから生成する。

退職所得控除の重複調整の例:

- 対象イベントID
- 過去イベントID
- 受取年月
- 金額
- 勤続/加入年数
- 勤続/加入開始日
- 勤続/加入終了日
- 既受給
- 退職所得控除使用済み
- 源泉徴収税額
- 市町村民税
- 道府県民税
- 重複年数
- 調整後控除

このfingerprintが変わった場合、以前の確認済みは無効とし、再び `確認推奨` に戻す。

## 7. 判定仕様

`退職所得控除の重複調整` の例:

1. 重複調整対象がない場合: `not_applicable`
2. 重複調整対象があり、現在fingerprintの確認済み記録がない場合: `review_recommended`
3. 重複調整対象があり、現在fingerprintの確認済み記録がある場合: `complete` または新状態 `reviewed`

推奨:

- 表示上は `確認済み` と出せるよう、新しい状態 `reviewed` を追加する。
- 必須入力の完了判定では、`reviewed` を完了扱いにする。
- `review_recommended` は次対象候補に入れる。
- `reviewed` は次対象候補から外す。

## 8. 保存・復元

確認済み状態は、シナリオデータと同じ保存経路に含める。

- ローカル版: 現行保存、JSONエクスポート、QNAP共有保存に含める。
- 公開版: LocalStorage、JSONエクスポート、サンプル移行に含める。

ただし、公開版にQNAP共有保存そのものは入れない。

## 9. 完了条件

- `退職所得控除の重複調整` を開き、内容を確認済みにすると、入力状況サマリーの黄色い次対象から外れる。
- 確認済み後も、詳細一覧では `確認済み` と分かる。
- 金額、年月、勤続/加入期間、既受給、控除使用済みなどを変更すると、再び `確認推奨` に戻る。
- カードを開いただけでは確認済みにならない。
- ローカル版と公開版の両方で同じ確認済み体験になる。
