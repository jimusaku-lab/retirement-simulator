# 計算ロジック保証基盤 設計メモ

## 目的

このアプリの税・社会保険・年金・投資・取り崩し計算について、利用者が「なぜその結果になったか」を検証でき、開発時にも計算ロジックの破損を早期検知できる状態にする。

「100%正しい」と口頭で保証するのではなく、次の3点を満たすことで、計算結果の信頼性を実務上検証可能にする。

- 計算に使った制度値・前提・丸め方が追跡できる
- 画面に出る計算式が、実際の計算ログから作られている
- 代表ケースと境界ケースを自動テストで固定し、変更時に差分が出る

## 保証対象

初期対象は、現在のアプリで資産推移に直接影響する次の領域とする。

- 公的年金: 65歳標準年額、月単位の受給開始、繰上げ・繰下げ、加給年金の試算
- 税: 所得税、住民税、復興特別所得税、普通口座利益の課税影響
- 社会保険: 国民年金、国民健康保険、後期高齢者医療、介護保険
- 投資: NISA実行額、NISA残り生涯枠、iDeCo受取、普通口座売却
- 世帯状態: 扶養、同居・別居、国保加入、介護保険、後期高齢者医療
- 取り崩し: 流動資金、追加投資、資産別残高、年次・月次キャッシュフロー

## 設計方針

### 1. 計算ロジックと表示式を分離しない

UI側で計算式を再実装しない。計算エンジンが、結果値と同時に「計算トレース」を返し、画面はそのトレースを表示する。

想定する形:

```ts
type CalculationTrace = {
  label: string;
  value: number;
  formulaText: string;
  inputLines: string[];
  resultLines: string[];
  ruleRefs: RuleReference[];
  rounding: string;
  warnings: string[];
};
```

これにより、表示式だけが正しく見えて、裏の計算が別物になる事故を防ぐ。

### 2. 制度値をルール台帳化する

税率、控除額、上限、均等割、軽減判定、年金調整率などは、コード内に直接散在させず、制度値として台帳化する。

最低限持つ情報:

- `domain`: 税、国保、後期高齢者医療、介護、年金、NISAなど
- `effectiveYear`: 適用年
- `jurisdiction`: 全国、東京都、大田区など
- `value`: 制度値
- `unit`: 円、率、月数、人数など
- `sourceLabel`: 出典名
- `sourceUrl` または `sourceNote`: 確認先
- `rounding`: 100円未満切捨て、10円未満切捨て、年額丸めなど

### 3. 年次計算と月次計算の境界を明確にする

年金の受給開始、扶養変更、国保加入変更は月単位で効く。一方、所得税・住民税の一部は年単位で判定される。

そのため、内部では次を分ける。

- 月次イベント: いつから入金・支出・加入状態が変わるか
- 年次集計: その年の所得、控除、保険料、税額をどう集計するか
- 表示年齢: 年末時点の満年齢を基本表示とし、必要に応じて「開始月時点」も併記する

### 4. テストは「計算単体」と「シナリオ全体」の2層にする

単体テストだけでは、画面上の資産激変のような全体破損を検知しきれない。次の2層を持つ。

- 計算単体テスト: 税、社会保険、年金、NISAなどの個別関数
- シナリオ回帰テスト: 代表シナリオを最後まで走らせ、90歳時点残高・資産寿命・主要年次値を固定

### 5. 差分は「異常」ではなく「要確認」として扱う

制度値更新や仕様変更で、計算結果が変わること自体はあり得る。重要なのは、意図しない差分を見逃さないこと。

差分が出た場合は、次を確認してから反映する。

- 差分が発生した年・月
- 差分が発生した項目
- 差分の原因となった入力、制度値、計算式
- UI表示式と実計算トレースの一致

## 導入工程

### Phase 0: 現在状態の保存

完了済み。現在の安定状態は GitHub に保存し、タグ `stable-next-tax-social-2026-05-12` を作成済み。

目的:

- いつでも現在の状態に戻れるようにする
- 今後の計算差分を比較する基準点にする

### Phase 1: 計算ロジック棚卸し

対象ファイル:

- `src/lib/simulation.ts`
- `src/lib/taxEngine.ts`
- `src/lib/pensionPlanner.ts`
- `src/lib/incomeEvents.ts`
- `src/lib/householdEvents.ts`
- `src/lib/retirementIncome.ts`
- `src/data/sampleData.ts`

作業内容:

- 各計算がどこで行われているかを一覧化する
- 制度値、丸め、年次・月次の扱いを洗い出す
- UI表示式がどの値を使っているかを確認する

成果物:

- 計算ロジック一覧表
- 変更してはいけない既存挙動のリスト
- 最初にテスト固定すべき重要ケースのリスト

このフェーズでは計算ロジックを変更しない。

### Phase 2: 代表シナリオの回帰テスト化

作業内容:

- 現在の個人用代表シナリオを、回帰テスト用の期待値として固定する
- 90歳時点残高、資産寿命、年金受給開始後の年次所得、税・社保、NISA実行額を確認対象にする
- 65歳受給、60歳繰上げ、扶養・国保変更ありのケースを含める

成果物:

- 代表シナリオの期待値テスト
- 計算変更時に差分が出る仕組み

合格条件:

- 既存の安定シナリオ結果が変わらない
- 変わる場合は、差分理由を説明できる

### Phase 3: 制度値台帳の導入

作業内容:

- 税・社会保険・年金の主要な制度値を台帳形式に移す
- 出典、適用年、自治体、丸め方を明示する
- 既存計算と同じ結果になるように移行する

成果物:

- ルール台帳
- 台帳を読む計算関数
- 既存結果との差分ゼロ確認

このフェーズも、原則として計算結果を変えない。

### Phase 4: 計算トレースの標準化

作業内容:

- 税・社会保険・年金の計算関数から、結果値と計算トレースを返す
- 画面の計算式ビューを、このトレースから表示する
- `max` や `min` は、内部計算ではそのまま使い、表示では「0円未満なら0円」「上限を超える場合は上限額」のように読める説明へ変換する

成果物:

- 計算トレース型
- トレース表示UI
- 表示式と実計算の一致テスト

### Phase 5: 境界ケーステストの追加

対象例:

- 所得が0円、控除額ちょうど、控除額を1円超えるケース
- 後期高齢者医療に切り替わる75歳前後
- 介護保険が始まる40歳、65歳前後
- 国民年金の対象・対象外が変わる月
- 扶養から外れる月
- 年金受給開始が60歳、65歳、75歳のケース
- NISA生涯枠を使い切るケース
- 普通口座売却益が出るケース

成果物:

- 境界ケースの自動テスト
- 丸め・上限・下限の確認

### Phase 6: UI監査ビュー

作業内容:

- 結果画面から、年次・月次の計算根拠を開けるようにする
- 各項目に「使った制度値」「式」「入力値」「結果」「注意点」を表示する
- 個人用では詳細表示を優先し、公向けでは標準表示と詳細表示を分ける

成果物:

- 計算根拠ビュー
- 年次・月次の任意期間診断表
- ルール出典表示

### Phase 7: 公開利用に向けた強化

個人用として十分でも、公に使うには次が必要。

- 自治体差の扱いを明示する
- 制度改定年の更新ルールを作る
- 入力値の妥当性チェックを強化する
- 免責と前提条件をUI上に明示する
- ユーザーごとの保存データを安全に扱う
- 誤入力時に資産推移が大きく崩れる場合、原因候補を表示する

## 導入時の安全ルール

- 1回の実装では1領域だけ触る
- 計算結果を変えないフェーズと、仕様として結果を変えるフェーズを分ける
- UI表示改善だけの変更でも、代表シナリオ回帰テストを通す
- 年金・税・社保の計算式をUI側で再実装しない
- 差分が出た場合は、原因が説明できるまで次へ進まない
- 各フェーズ完了時に GitHub へ保存する

## 最初に実施する作業

次に進めるべき作業は Phase 1 の棚卸し。

具体的には、計算ロジック一覧表を作り、以下を確認する。

- どのファイルがどの計算責任を持っているか
- 制度値がどこに書かれているか
- 年次計算と月次計算がどこで接続されているか
- 表示用の式が実計算と同じ値を使っているか
- 代表シナリオとして固定すべき出力値は何か

この棚卸しが終わるまで、計算ロジック本体には手を入れない。
